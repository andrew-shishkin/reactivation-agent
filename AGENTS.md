# Агент реактивации закрытой базы

Этот файл читают Claude Code и Codex. В нём порядок работы, от которого нельзя
отступать. Задача агента — пройти по проигранным сделкам, отбросить мёртвые
и безнадёжные, найти у живых свежий повод и подготовить по ним тёплые письма.

**Кто перед тобой.** Пользователь — продавец, руководитель отдела продаж или фаундер,
не программист. Он не открывает терминал и не правит код. Все команды запускаешь ты
сам, ему показываешь только итог одной-двумя фразами. Если без его действия не обойтись
(вставить ключ в файл, утвердить письма) — даёшь инструкцию по шагам, где каждый шаг —
одно понятное действие, и говоришь, что он должен увидеть после него.

Называй всю систему **агентом**: «агент реактивации», «агент проверил базу».
Не «навык», не «скрипт», не «пайплайн».

## Три правила, которые важнее всего остального

**1. Данные не идут в твой контекст.** База может быть на тысячи сделок. Если ты
будешь её читать, ты сожжёшь лимиты пользователя за один заход.
- Работу с данными делает код: `node run.js …`. Ты читаешь только его короткие сводки.
- Пачки `work/*.jsonl` читают субагенты, не ты. Ты передаёшь им пути к файлам.
- Не открывай `state/` (база прогона), `out/к-отправке-*.csv` и `.env` — никогда,
  даже если пользователь попросит «посмотреть, что там». Покажи ему, где файл лежит,
  пусть откроет сам.
- Прогон на тысячу сделок должен стоить тебе столько же токенов, сколько на двадцать.

**2. Персональные данные клиентов не уходят в модель.** По закону о персональных
данных (152-ФЗ) имена, почты и телефоны клиентов-физлиц не должны попадать на
серверы провайдера модели. Поэтому:
- код хранит контакты в отдельной таблице на компьютере и закрывает имена, почты
  и телефоны в истории сделок ещё при загрузке;
- письма пишутся с заглушкой `{{имя}}`, настоящее имя подставляет код при выдаче;
- не проси пользователя прислать выгрузку в чат и не вставляй куски базы в свои ответы;
- если пользователь сам прислал в чат имя или почту клиента — не повторяй их и не
  записывай никуда, кроме как через код.

**3. Наружу — только после «да».** Задачи в CRM и письма клиентам — необратимые
действия. Агент готовит черновики, человек их утверждает, и только потом
`node run.js deliver`. Сделки в CRM агент не меняет и не удаляет вообще.

## Шаг 0. Подготовка — при первом обращении

Проверь сам, без вопросов пользователю:

```
node run.js doctor
```

**Node.js нет или версия ниже 22** — поставить его за пользователя нельзя.
Дай инструкцию под его систему:
- Mac: открыть https://nodejs.org, скачать кнопку LTS, запустить файл, нажимать
  «Продолжить», в конце ввести пароль от компьютера;
- Windows: открыть https://nodejs.org, скачать кнопку LTS, запустить файл, нажимать
  «Next», в конце «Install».

Попроси написать «готово» и проверь снова. Дальше не иди, пока Node.js не появится.

**Node.js на месте** — создай рабочую папку `my/` из заготовок (если её ещё нет):

```
mkdir -p my && cp -n templates/config.json templates/offer.md templates/signals.md my/
```

На Windows без bash: `mkdir my`, затем `copy templates\config.json my\` и так же
остальные два файла. Скажи одной фразой, что агент готов к настройке, и переходи к анкете.

## Шаг 1. Анкета

Агента собираешь под конкретного человека. Спроси всё ниже, **по одному-два вопроса
за раз**, простыми словами. Где есть варианты — дай их выбором (в Claude Code —
вопросом с кнопками). Чего человек не знает — ставь значение по умолчанию
и говори, какое.

1. **Что продаёте, кому, как обычно проигрываете.** Тон писем (на «вы» или на «ты»)
   и подпись. Если есть письмо, на которое клиенты отвечали, — пусть пришлёт:
   это лучший образец. → `my/offer.md`.
2. **Откуда брать сделки.**
   - *Битрикс24* — нужен входящий вебхук с правами на CRM и задачи. → `source: "bitrix"`.
   - *amoCRM* — нужен долгосрочный токен интеграции и поддомен. → `source: "amo"`.
   - *Другая CRM с API* — нужен API-ключ; выгрузку под неё ты пишешь сам (см. ниже).
   - *Файл* — выгрузка сделок в CSV или Excel. → `source: "file"`.
   Если CRM ещё не подключена — дай ссылку на гайд https://outreacher.co/guide-crm,
   там по шагам, где взять ключ под каждую CRM. Если CRM подключена к ассистенту
   только коннектором (HubSpot, Pipedrive и другие) — для этого агента проще выгрузить
   файл: коннектор гонит каждую сделку через твой контекст. В выгрузке-файле у большинства
   CRM нет истории комментариев — тогда предупреди, что повод из заметок агент будет
   искать только по причине проигрыша.
3. **Как найти проигранные.** Для файла со всеми сделками — как называется стадия
   проигрыша (`lost_stage`). Есть ли отдельное поле причины отказа, где лежит ИНН —
   для CRM это коды полей в `crm_fields`.
4. **Окно давности.** По умолчанию 6–18 месяцев: свежие ещё помнят отказ,
   старые уже не помнят нас. → `window_months`.
5. **Каких проигранных не трогать.** Дубли, спам, тест, нецелевые — уже в списке.
   Что ещё: «просили больше не писать», «конкуренты»? → `exclude_reasons`.
6. **Где клиенты.** Россия → проверка статуса компании в ЕГРЮЛ по ИНН. Для этого нужен
   бесплатный ключ DaData (dadata.ru, 10 000 проверок в сутки бесплатно). Выручку за
   два года даёт DataNewton (datanewton.ru, при регистрации 200 запросов) — по желанию.
   Клиенты за рубежом → `country: "other"`, проверка только по сайту и новостям.
7. **Что для вас повод написать.** Покажи список сигналов из `templates/signals.md`
   коротко, одной строкой каждый, и спроси, какие важны и какие свои добавить
   (новая стройка, тендер, сезон…). Самому важному — вес 5, обычным — 3, слабым — 1–2,
   ненужным — 0. → `signals` в `my/config.json` и описание в `my/signals.md`:
   оставь там только выбранные, свои допиши по тому же образцу.
8. **Куда отдавать результат.**
   - *Файл для менеджеров* — таблица с письмами, именами и почтами. → `delivery.mode: "file"`.
   - *Задача в CRM ответственному* — с поводом и черновиком письма (Битрикс24 и amoCRM).
     → `"crm"`.
   - *Отправка с вашей почты* — после утверждения, не больше `daily_limit` писем в день
     (по умолчанию 30, с паузой 20–40 секунд между письмами). Нужны адрес SMTP-сервера,
     ящик и пароль приложения. → `"email"`.
9. **Какая у вас подписка.** От неё зависят модели и размер одного захода.
   - Claude: дешёвая модель для субагентов — `haiku`, письма — `sonnet`. Это уже
     записано в `.claude/agents/`, менять не нужно.
   - Codex: открой список моделей своего аккаунта (команда `/model`) и впиши
     в `models.codex` облегчённую модель (обычно с «mini» в названии) как `cheap`
     и основную как `strong`. Модели по памяти не называй — только из списка.
   - **Посоветуй переключить основную сессию** на модель попроще (в Claude — Sonnet,
     не Opus; в Codex — без максимального уровня рассуждений): главный агент только
     раздаёт работу и читает сводки, тяжёлой модели ему не нужно.

После анкеты покажи пользователю итог настроек пятью-шестью строками и спроси «всё так?».

### Ключи — только в файл .env

Если нужен ключ (вебхук, токен, DaData, почта):
1. Создай `.env` из шаблона, если его нет: `cp -n .env.example .env`
   (Windows: `copy .env.example .env`). Если `.env` уже есть — не перезаписывай.
2. Открой его пользователю в обычном редакторе: на Mac `open -e .env`,
   на Windows `notepad .env`.
3. Скажи, в какую строку после знака «=» вставить какой ключ, без пробелов и кавычек,
   потом сохранить, закрыть и написать «готово».
4. Проверь через `node run.js doctor` — он показывает «ключ вписан», не показывая ключа.

Сам `.env` не читай и ключи в чат не проси. Если пользователь прислал ключ в чат —
скажи, что так делать не стоит, и попроси вставить его в файл.

### Другая CRM с API

Готовые выгрузки есть для Битрикс24 и amoCRM (`src/crm/`). Для другой CRM напиши
`src/crm/<имя>.js` по их образцу: функция `exportLost(cfg, log)` возвращает массив
сделок того же вида, что `bitrix.js`. Методы API бери из официальной документации
CRM, не по памяти. Ключ — из `.env`. Подключи в `run.js` рядом с `bitrix` и `amo`.

## Шаг 2. Пробный заход на 10 сделках

Прежде чем гнать всю базу, покажи результат на маленьком куске.

```
node run.js import --file <путь>      # или --crm bitrix | --crm amo
node run.js filter
node run.js check --limit 10
node run.js batch next context --size 10
```

Отдай пачку субагенту **reactivation-reader** (дальше — по схеме из шага 3), затем
сигналы на этих же сделках, `score`, письма на три лучших. Перед заходом и после
попроси пользователя посмотреть расход лимита (в Claude — Settings → Usage,
в Codex — `/status`) и прикинь, сколько сделок помещается в один заход.
Запиши это в `my/config.json` через размеры пачек и `letters_per_pass`.

Покажи пользователю: сколько сделок отсеялось и почему, у кого нашёлся повод
(компания + повод одной строкой, без имён), и где файл с письмами. Спроси, то ли это.

## Шаг 3. Рабочий заход

Один заход — это всё ниже по порядку. Каждая команда берёт только необработанное,
поэтому заход можно прервать где угодно и продолжить в следующей сессии.

```
node run.js batch reset          # в начале сессии: отпустить пачки, брошенные в прошлый раз
node run.js import …             # если база в CRM — подтянуть новые проигранные
node run.js filter
node run.js check
```

**Чтение истории.** Получи пачку:

```
node run.js batch next context
```

Команда напечатает путь к пачке и путь для ответа. Запусти субагента
**reactivation-reader** с задачей «Пачка: <путь>. Ответ: <путь ответа>».
Возьми сразу несколько пачек и запусти по субагенту на каждую **параллельно** —
сколько указано в `batch.parallel`. Одна пачка — один субагент, не по субагенту
на компанию: у каждого субагента свой стартовый расход. Когда субагент закончил:

```
node run.js batch save <путь ответа>
```

Повторяй, пока `batch next context` не скажет, что больше ничего нет.

**Сигналы** — так же, шаг `signals`, субагент **reactivation-scout**.

**Баллы:** `node run.js score`.

**Письма:**

```
node run.js letters next
```

Субагент **reactivation-writer**, затем `batch save`. После всех пачек:

```
node run.js letters review
```

Скажи пользователю открыть `out/письма-на-проверку.md` и ответить, какие письма
убрать или поправить. Правки вноси через автора писем: верни письмо в работу
(`letters reject <номер>` и новая пачка), сам текст писем в чат не пересказывай.
Когда пользователь утвердил: `node run.js letters approve all` (или номера)
и `node run.js deliver`.

**В Codex** при запуске субагента передавай модель явно: для reader и scout —
`models.codex.cheap` из `my/config.json`, для writer — `models.codex.strong`.
Если там пусто — сначала заполни (шаг 1, вопрос 9).

**Лимиты кончаются посреди захода** — остановись после `batch save` текущих пачек,
покажи `node run.js status` и скажи, что в следующий раз агент продолжит с этого места.

В конце захода — `node run.js status` и `node run.js export`, и пользователю
три-четыре строки: сколько проверено, сколько отброшено, у скольких повод, сколько писем
готово. Итоговая таблица — `out/итог.csv`, в ней нет имён и почт.

## Шаг 4. Регулярный запуск

Закрытая база пополняется каждую неделю, а у старых сделок появляются новые поводы.
Предложи запуск раз в неделю или раз в две:
- новые проигранные проходят весь путь заново;
- по тем, у кого повода не было, сигналы ищутся снова: `node run.js recheck --days 30`.

Расписание настрой средствами того ассистента, в котором работает пользователь
(запланированные задачи в Claude, автоматизации в Codex). Сверься с его актуальной
документацией, по памяти не обещай. Письма и при регулярном запуске не уходят без
утверждения: регулярный запуск готовит черновики и сообщает, что они ждут проверки.

## Если что-то пошло не так

- Команда упала с ошибкой — прочитай текст ошибки, она на русском и говорит, что делать.
  Ключ не подходит — проведи пользователя через `.env` заново.
- Субагент вернул не всё — `batch save` отпустит недостающие сделки в следующую пачку.
- Пользователь хочет поменять настройки (окно, сигналы, веса) — правь `my/config.json`
  и `my/signals.md`, затем `node run.js filter` и `node run.js score` — они пересчитают
  без повторной проверки сайтов.
